This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

מה בי״ם ("Mah Ba'im") is a youth activities/clubs/events discovery PWA for teens in Jerusalem. It's a working prototype: a single-file HTML/CSS/JS frontend backed by Supabase (Postgres + Auth + Storage), deployed via GitHub Pages.

- Live app: https://noarappproject.github.io/ma-byam_1.0/
- Supabase project ref: `soncpzmasqcjxcawhqqw` (URL and publishable key are hardcoded in `docs/index.html` — see Notes below)
- Test login: `testuser_mb1` / `test1234` (verified working 2026-09-17). **`admin` / `123456` no longer works** — the row still exists but the password was changed at some point, and the auth endpoint returns 400; it was documented here for a long time and cost real debugging time, so don't reinstate it without testing it first. Many other throwaway accounts exist in `public.users` from development; most have unknown passwords.
- **The Supabase project is on the free tier and pauses itself after roughly a week of inactivity.** When paused its subdomain stops resolving entirely (`nslookup` returns NXDOMAIN) and `supabase projects list` reports `INACTIVE`. Nothing is lost — restoring from the dashboard brings the data back intact — but it cannot be restored from the CLI; it takes a click on **Restore project** at https://supabase.com/dashboard/project/soncpzmasqcjxcawhqqw. Symptom to recognise: every DB call fails while guest browsing still works perfectly.

## Commands

There is no build step for the app — `docs/index.html` is edited directly and is live as-is (open it in a browser, or serve `docs/` with any static file server).

- `npm run make-icons` — regenerates the PWA icons in `docs/icons/` from `tools/make-icons.mjs` (uses `sharp`; the only dependency in the project).
- `supabase db push` — applies pending files in `supabase/migrations/` to the linked Supabase project (CLI must be logged in and linked).
- `supabase migration new <name>` — scaffolds a new timestamped migration file.
- No automated test suite or linter is configured.
- Deployment is automatic: pushing to `master` updates GitHub Pages, which serves directly from the `/docs` folder.

## Architecture

### Frontend: one file, no framework

`docs/index.html` (~3400+ lines) is the entire frontend: plain HTML/CSS/JS in a single `<script>` block, with the Supabase JS client loaded from a CDN. There is no router — every screen (auth, onboarding questionnaire, home, activity archive, favorites, social, profile, settings, another user's profile, followers/following list) is a sibling `<div class="frame" id="...Screen" hidden>` in the body, and a `showX()` function makes one visible by setting `.hidden = false` on it and `= true` on every other screen. **Adding a new screen means adding it to every existing `showX()` function's hide-list**, not just writing its own show function.

- **The bottom nav is context-dependent, not a fixed set of tabs.** Guests get `בית`/`הגדרות` (2 tabs, unchanged since the app's early days). Logged-in users get `בית`/`מועדפים`/`חברתי`/`פרופיל` (4 tabs) — **Settings has no bottom-nav tab for logged-in users**; it's reached via the cog button (`ICONS.gear`) at the top right of the Profile header, and while Settings is open the nav marks **פרופיל**. `showApp()` sets `navSettingsEl.hidden = !guest` (and `navFavoritesEl`/`navSocialEl`/`navProfileEl.hidden = guest`) to implement this split. Any new top-level destination needs to decide which of these two patterns (persistent nav tab vs. Profile-header icon) it belongs to.
- **Palette (2026-10-21, chosen by the product owner): butter-yellow ground, cyan blue and black for type and actions, forest green used sparingly, muted gold (not a glowing yellow) for ornaments and ratings.** Tokens on `:root` (`--bg`, `--accent`, `--ink`, `--forest`, `--gold`, `--stone`), redefined for dark mode on a near-black ground; the direction note at the top of `<body>` records it. 11 category inks (`--cat-*`, same family) are selected by `data-cat="<category>"`, **never** by an inline style. The `[data-cat]` catch-all rule must stay **above** the named `[data-cat="x"]` rules (equal specificity — a trailing catch-all would win). **No halftone dots, grain or misregistered ghosts anywhere** — the owner rejected them; all art is flat shapes drawn in this file (nothing copied, nothing under someone else's copyright).
- **Activity imagery: a real photo only if the organizer's own page shows it, otherwise a generated flat poster.** `categoryArtSvg(a)` draws a per-category poster (light silhouette, one darker form, a gold disc placed per activity id). `plateArtHtml(a)` shows `a.image_url` over it when set. The scraper keeps an `image_url` only if that exact URL is an `<img>` on the item's own page (`ClubPage.images` in `withClubPage()`), never one the listing extraction supplied. The welcome screen draws, in the login plate's manner and unframed, the Western Wall (courses of rounded stones, smaller above and large below, each offset, plants hanging from a few joints) with the Tower of David on the left and the Dome of the Rock on the right, the gold sun between them touching neither, a forest and a lighter concave band of grass in front with three small stone houses on them — no shapes that are not part of the scene; the signup screen draws the Mishkenot Sha'ananim windmill, the login screen the light rail among stone houses.
- **Home fits one phone screen at the top: search, three compact post carousels, a category filter, then the full list.** The carousels, in order, are **המלצות עבורך** (`recommendedActivities()`), **פעילויות השבוע** (`weekActivities()`: open activities meeting between today and Saturday inside their season, or one-offs dated in it) and **חדש** (`newestActivities()`), each at most `POSTS_MAX` (5) posts. A post (`postHtml`) shows one activity at a time; a swipe moves exactly one (`scroll-snap-stop: always`), a mouse drag moves one (`wirePosts`), and the dots under it pick a post, the current one in cyan. Below them `renderHomeAll()` renders category chips (`homeState.category`) and every activity, soonest first, as `favRowHtml` rows. Each carousel's archive link opens `showArchive("all"|"week"|"new")`. scrollLeft runs negative in RTL, so positions are read off its magnitude and written with `postsDir()`.
- **Activity detail is a real full screen** (`detailScreen`), not a modal: full-bleed plate, a sheet lifted over it, and a docked register CTA that cannot scroll out of reach. `factRowsFor(a)` and `ctaForKind(a)` are keyed off `item_kind`/`schedule_type` (חוג / אירוע / פעילות) so a weekly club shows its rhythm and an event shows its single date; `a.status` outranks the kind, so a full/cancelled/ended activity never renders a register invitation. `renderDetailFriends()` shows only real data — people you follow who favorited it, read from `followedFavoritesByActivity` — and there is deliberately no fabricated attendance count, because the product has no registration tracking.
- **"Friends who saved this" is next to every activity, everywhere the activity appears — not just its own detail screen, and independent of whether the viewer saved it too.** Instagram-style: it names people (`t.savedByLine(names, total)` — "X saved this" / "X ו-Y שמרו את זה" / "X ועוד N"), not just a count, with a tight overlapping avatar stack (`.mini-avatar-stack .avatar-xs`, 19px, borrowed from the same `.avatar` system as everywhere else). Every interpolated username goes through `bidiIsolate()` (Unicode FSI/PDI) before it reaches any of the four STRINGS entries — a bare Latin name dropped into an RTL sentence is exactly the case the bidi algorithm garbles, and fixing it once at the point names are built beat hand-tuning spacing per language. `followedFavoritesByActivity` is a module-level `Map<activityId, users[]>` batch-loaded once by `loadFollowedFavoritesMap()` (two queries: accepted followees, then their favorite rows, joined client-side) rather than one query per card — the same shape as `favoritedTopicsAndCategories()`. `followedFavoritesFor(id)` is the synchronous read; `friendsMetaHtml(id, metaClass)` renders the compact card version by borrowing whichever meta-row class the caller already uses (`card-lg-meta` / `card-sm-meta` / `fav-row-meta`), so it reads as one more fact line rather than a bolted-on widget, while the detail screen keeps its own larger `.friends-row` treatment — and there it is a way in: one person makes the whole row a button, several make each face and the named link a button, and `openProfileFromDetail()` opens that profile with a back button that restores the screen underneath and reopens the activity. The map is reloaded on login, cleared on sign-out/guest, and reloaded inside `followUser()`/`unfollowOrCancel()` (not `approveRequest()`/`denyOrRemove()`, which change who follows *you*, not who you follow) — so it can lag a currently-open screen by one render but is never stale across a screen change. Relies on the existing `favorites_select_visible` RLS (a follower may already read an accepted followee's rows) — no schema change needed. **The seeded demo data for this is thin** — see HANDOFF.md's Test login section (`demo_noa1`/`demo_itay1`) before assuming the feature is broken because a fresh account sees nothing.
- **Reviews are a star rating plus an optional 100-character note**, read by anyone and written only by an account. The summary row on the detail sheet (`renderReviewsBlock()`) is itself the `<button>` that unfolds the list — a real `<button>`, unlike the cards, because nothing interactive is nested inside it. A review posts **under the writer's name** unless they tick "anonymously"; anonymity is opt-in in the UI but **the `is_anonymous` column still defaults to true**, and that mismatch is deliberate — a row that somehow reaches the table without the field set should hide a name nobody meant to hide rather than publish one that cannot be taken back. Whichever way it is set, it is enforced in the database rather than here: the list arrives from the `activity_reviews_public()` RPC with the author already stripped from anonymous rows, so the client never holds an identity it would have to be trusted not to render (see Backend). `emptyReviewDraft()` is the single place the UI default lives, and `loadReviews()`'s "has the user started editing?" test compares against it rather than against a literal `true`/`false`, so flipping that default again cannot quietly invert the check. `escHtml()` exists for this feature — a review body is the first free text in the app that one user can put on another's screen, and everything renders through `innerHTML`, so it must be escaped at the seam. The form paints synchronously from `reviewDraft`, which is why `resetReviewState()` seeds an empty draft instead of null; `loadReviews()` will not overwrite a draft the user has already started typing, and the post-load re-render is skipped entirely while the textarea has focus.
- **Saving repaints one control, never a screen.** `refreshFavoriteAffectedUI(activityId)` flips the matching `[data-fav-id]` buttons in place; a full re-render would reset rail scroll, replay every entrance animation, and yank the row out from under the thumb that tapped it. The Favorites list is the one place membership changes the list, so `reconcileFavoritesList()` collapses the removed row in place before re-rendering. The screen has no "N activities" line: each filter chip carries its own count instead — `הכל (n)`, `<category> (n)`, and the topic chips count within the chosen category.
- **Cards are `role="button"` divs, not `<button>`.** They contain a nested save control, and a `<button>` inside a `<button>` gets hoisted out by the HTML parser, breaking both. Keyboard support is explicit (`cardKeyHandler`).
- **Icons are drawn SVG in one `ICONS` registry** — never emoji, including in the bottom nav. Favorites uses a heart (`ICONS.heart`) and the app's vocabulary for it is *saving* ("שמורים" / "מה ששמרתי"), not pinning; `ICONS.pin` is location and must stay visually distinct. (Was a ribbon bookmark shape before; only the shape changed, not the vocabulary or the `--stamp` fluoro-pink fill it takes when saved.)
- **The profile has a channel-style banner.** `users.banner_url` (migration `20260901180000_add_profile_banner.sql`) is optional; when null, `bannerHtml()` renders a generated per-user risograph banner, so a null banner is the designed default rather than a missing asset. Banners reuse the public `avatars` bucket at `<user_id>/banner.<ext>`, inheriting its path-scoped owner-only RLS — no new bucket. `uploadProfileMedia()` serves both avatar and banner and validates type and a 5MB ceiling.
- **The profile is four views on one screen, switched by `profileMode`** (`showProfile(mode)` loads and opens it; `switchProfileMode()` changes view without reloading). **view** (`renderProfileView`): banner with the cog at its top right, avatar, the **display name** in large type with clear space under the banner, `@username` under it, the follower / following / saved counts (`profileStatsHtml()`; on your own profile they open the follow lists and Favorites), a small **פרטים** pill (text only), interests, a **מועדפים** button to the Favorites tab, the earned achievements (mark + name only) and a **הישגים** button. No name · age · area line. **details** (`renderProfileDetails`): no card — it sits on the paper itself. An island of trees (`isleArtSvg(DETAILS_ISLE)`), the display name with `@username` under it, then **פרטים אישיים** as a small green heading with an olive sprig (`sprigSvg()`) over first/last name, age/grade and area, two to a row; the profile type (פרטי / ציבורי) on a row of its own; interests and activity types; a small grove (`groveArtSvg()`) to close. The **עריכה** pill sits opposite the back button; leaving or saving the form returns here. **achievements** (`renderAchievementsPage`, owner only): all 21, five to a row, earned in colour and locked in grey with a lock, each with name and condition, under a header of hills and cypresses (the Wall and the Dome belong to the welcome screen and are not repeated). **Someone else's profile** (`renderOtherProfile`): display name, `@username`, the counts (read-only, from the `profile_counts()` RPC — `follows` is readable only by its two participants, so counting from the client undercounts), the follow button, interests, favourites and earned achievements. If it is private and the viewer is not an approved follower, the favourites, picture and banner are hidden (`canViewProfile()`) and a lock note says why; everything else still shows. Their interests come from the `profile_interests()` RPC, because `user_preferences` is owner-only (it also holds names, age and area).
- **Display name vs username.** `users.display_name` (any language, up to 30, null = show the username) is what a profile shows large; `displayNameOf(u)` is the one fallback, used for user rows, the "saved by" lines, the greeting and reviews (`activity_reviews_public()` returns it too). It is changed in the edit form. **The username never changes after sign-up** — the edit form has no field for it; it is the login and the `@handle`. User rows show `@username` under a display name when one is set, and `searchUsers()` matches either (`username.ilike.q*` or `display_name.ilike.*q*`, with PostgREST's reserved characters stripped from `q`).
- **The questionnaire is three parts on every screen** (`renderQuiz()`): the question at the top (`.qz-main`), an island of trees in the room left over (`.qz-scene`, one drawing per screen in `QUIZ_ISLES`), and the buttons at the bottom where the thumb is (`.qz-foot`, sticky, with the skip link under them). The island is a size container and disappears below 84px, so a long step (topics, large text, a small phone) gives up the drawing first and scrolls under the pinned buttons. The opening screen is the welcome screen's **מה בי״ם** mark, **בואו נכיר!**, one sentence and a smaller "אפשר לדלג בכל שלב."; the closing screen repeats the mark — no emoji.
- **Decorative trees** come from three drawings: `isleArtSvg()` (a floating island — grass over brown earth with stones — carrying olive trees, cypresses, bushes, flowers and optionally a sun, birds, a signpost or sparks; trees are `[kind, x, size]`), `sprigSvg()` (an olive sprig beside small headings) and `groveArtSvg()` (a tapered mound with a few trees). Trunks and earth use `--bark`, leaves `--forest` and `--cat-wellbeing`. Drawings end in curves, never a straight-edged block — the owner rejects rectangles that aren't part of the picture.
- **Achievements** are defined in `ACHIEVEMENTS` (key, icon, ink) with names and conditions in `STRINGS.*.achievements`, and recorded once each in `user_achievements`. `runAchievementCheck()` (debounced through `checkAchievements()`) derives most of them from data already in memory — favourites, `favoritedAt`, the activities' categories, places, prices, `created_at` and `registration_deadline`, `followedFavoritesByActivity`, `myPrefs`, follow counts — and is called after saving an activity, uploading media, the questionnaire, a profile save, a follow change and on every sign-in. Moments are awarded where they happen: sorting favourites (`organized`), approving a request (`open_door`), following from the suggestions (`widen_circle`), following someone with no shared interest (`beyond_bubble`, via the `shared_interest_counts()` RPC, which returns counts only), and saving changed preferences 30+ days after `user_preferences.completed_at` (`changed`). App opens and the first use of search and of a filter are logged to `user_events` (`logUserEvent()`). Questionnaire topics map to categories by position (`TOPIC_CATEGORIES`; the four languages list them in the same order). Guests earn nothing.
- **`showNotice()` is the top notice**: a black banner that slides down from the top in both themes, one at a time from a queue, tap to dismiss. An achievement shows "השגת את ההישג "שם"" with its condition underneath; an oversized image (over 5MB) uses it too, instead of a hint printed under the upload.
- **No colour themes.** Per-app and per-profile palettes were added and removed again (2026-10-23, owner's call); the app keeps the one palette above, in light and dark. **Text size** is in Settings under **נגישות**, a three-way control like the light/dark one (קטן / רגיל / גדול, default רגיל), driving `--text-scale`; there is no separate accessibility screen any more.
- **The edit form follows the details page.** Banner and avatar at the top (changed on themselves), then display name beside the username (shown in a dashed box with a lock — it can't change), **פרטים אישיים** two to a row (`.pf-grid`) with the area under them, profile type in its own section as a פרטי/ציבורי segmented control (`profileState.isPrivate`, part of the snapshot, written to `users.is_private` on Save — Settings still has the same switch), interests, activity types, and the new password last.
- **Profile edit is a form with a sticky press bar, not a scroll with a button at the end.** Its own `pf-*` CSS namespace replaced the old `.edit-*` block: the bar carries the title and the only Save, sections are ruled bands on the paper ground rather than nested cards, and text inputs, selects and chips share one field grammar (the questionnaire now uses the same `pfTextFieldHtml`/`pfSelectHtml`/`pfChipsHtml` fields). Save is gated on `profileBaseline` — a JSON snapshot taken by `enterProfileEdit()` and compared by `profileEditSnapshot()` — so it stays disabled until something differs and the discard link knows whether it is throwing work away; media is excluded from that comparison because an upload commits the moment a file is picked. A chip tap re-renders its section, so the new-password input is parked on the module-level `profileEditPassword` rather than read back off the DOM. The credential fields are an LTR island (`.pf-pass-wrap { direction: ltr }`) so `inset-inline-end` and `padding-inline-end` land on the same side as the latin value.
- **`body { direction: rtl }` overrides `html[dir]`**, so English and Russian lay out right-to-left app-wide with their punctuation on the wrong end. `#profileContent` opts out; the global fix is the same rule on `body`, deliberately not applied yet because it reflows every screen.
- **`loadAndApplyProfile()` tolerates schema lag.** `docs/index.html` ships via GitHub Pages independently of `supabase db push`, so the frontend can be newer than the DB. Selecting a not-yet-migrated column fails the whole row and used to blank the entire profile; the loader now retries with `PROFILE_BASE_COLS` so a missing new column degrades to "not set". Add new optional columns to `PROFILE_NEW_COLS`.
- **Personalization is scored client-side from data already on hand** — `user_preferences.interest_topics` (from the onboarding quiz, kept in the module-level `currentInterestTopics`), the topics/categories of the user's own favorited activities (`favoritedTopicsAndCategories()`), and `friendSaveBoost(a)`: `FRIEND_SAVE_WEIGHT` (4) per person you follow who saved an activity you haven't — a real person's choice outweighs an inferred topic match, and it's deliberately linear so each additional friend pushes the card further forward. The boost only applies to activities you haven't saved yourself; once it's in your own favorites the "friends surfaced this for you" job is done. There is deliberately no separate search-history tracking table; `recommendedActivities()` falls back to soonest-first ordering for guests or signed-in users with no signal of any kind — quiz, own favorites, or friends'.
- **Social tab** (`showSocial()`/`renderSocial()`, logged-in only; its nav icon is a magnifying glass, and it no longer shows a following count) consolidates what used to be two separate Profile-header icons (🔔 notifications, 🔍 user search — both removed, along with their screens) into one screen: a user search box, an incoming-follow-requests list, and a "who to follow" section (`recommendedUsers()`, scored by shared `interest_topics`, with a client-side-only per-session dismiss list). Opening someone's profile from Social (or from Favorites/Home) sets the module-level `returnToScreen` so that profile's back button returns to wherever it was opened from, instead of always assuming Profile.

Patterns worth knowing before editing this file:

- **State is module-level and per-screen, not componentized.** The Archive screen's filter state (`archiveState`) and the Favorites screen's filter/sort state (`favState`) are separate globals. Each screen's render function (`renderHome()`, `renderArchive()`, `renderFavorites()`, `renderProfile()`, `renderSettings()`, `renderSocial()`, …) fully replaces its container's `innerHTML` on every call and re-attaches listeners on the elements it just created; listeners on static containers (search inputs, chip rows) are instead registered once, at top level, using event delegation.
- **Declaration order matters for top-level statements.** The whole script executes top-to-bottom before `boot()` (the final IIFE at the bottom of the file) triggers any real interaction. A `const el = document.getElementById(...)` referenced inside a *function body* is safe regardless of where in the file it's declared (hoisting covers it), but one referenced in an *immediately-executed* top-level `el.addEventListener(...)` call must be declared earlier in the file than that call, or it throws (temporal dead zone).
- **Type is Rubik (display) + Assistant (body), with Noto Sans Arabic behind both** for the Arabic locale; the old Suez One / Heebo pair is gone. Every headline uses the `.display` / `.display-xl|lg|md|sm` scale rather than a bare `h1`.
- **Hebrew copy addresses everyone the same way.** No slashed forms (`שמר/ה`) and no masculine imperatives (`נסה`, `בחר`, `הוסף`): second-person past (`שמרת`, `עקבת` — written the same for both), infinitives and nouns for buttons (`שמירה`, `הוספה`, `מעקב`), impersonal phrasing (`אפשר לנסות שוב`), and nouns for achievement names (`סקרנות`, `לעומק`). New strings follow the same rule.
- **i18n** lives in a single `STRINGS` object keyed by `he`/`ar`/`en`/`ru` (Hebrew is default and RTL, Arabic is RTL, English/Russian are LTR). `L()` returns the current language's dict — there is no fallback, so a key missing from any one of the four blocks renders literal `undefined`. Static text is applied once per language switch via `applyStaticText()`; each dynamic screen re-renders itself from inside `setLanguage()`. Activity content (titles, descriptions) is never translated, only UI chrome is.
- **Signup checks a field when the user is done with it, not while typing.** `checkUsernameField()` runs when the username field loses focus (moving to the password, or pressing a button): first the format, then `usernameTaken()` (case-insensitive, because the hidden e-mail is lower-cased) — red under the field if it fails, green if the name is free. The password is checked on blur too, and submit shows every problem at once; typing in a field only clears its message. Usernames: English letters, digits and `_`, 3–20 (`USERNAME_RE`). Passwords: English letters, digits and simple symbols, 6–20, at least one letter and one digit (`PASSWORD_RE`). Messages say only what went wrong, briefly ("שם המשתמש חייב להיות באורך 3 תווים לפחות.", "הסיסמה חייבת להיות באורך 6 תווים לפחות ולהכיל לפחות אות אחת ומספר אחד."); the 20-character cap is `maxlength` on the inputs and is never announced. Login keeps one combined message so it never reveals which of the two was wrong.
- **Auth is username-based on top of Supabase's email/password auth.** Signup synthesizes a placeholder email (`<username>@mahbaim.app`); login looks up the user's real stored email from `public.users.email` by username rather than re-deriving it. Usernames are fixed after sign-up, so the placeholder email never needs to follow one (`supabase.auth.updateUser({email})` would reject the change under this project's email-confirmation settings anyway). Guest mode is a pure `localStorage` flag (`mb_guest`) with zero Supabase writes; guest theme/text-size/language preferences persist to `localStorage` only.
- **The activities list is read from the database, with the last good copy kept on the device.** `activities` is a module-level `let`, seeded synchronously from `localStorage` (`mb_activities_v1`) by `readActivitiesCache()`, then replaced by `loadActivities()` — which `boot()` starts first and does not await, since the catalog needs no session. Stale-while-revalidate: screens paint from the device copy immediately, and `refreshActivityScreens()` repaints only if the live rows differ, so the usual case costs no repaint, no rail-scroll reset and no replayed entrance animation. A failed fetch never overwrites the copy — that copy is what keeps the catalog visible while the free-tier project is paused. Only the columns the screens read are fetched (`ACTIVITY_COLS`, ~22 KB for 22 rows), not the whole 48-column table; a new field the UI starts reading has to be added there or it will be `undefined`. `activitiesStatus` is `"ready"` whenever there is anything to show; the other three states (`"loading"`, `"unavailable"`, `"empty"`) only ever describe a device with nothing cached, and swap Home's two rails (and the Archive list) for one `dataNoticeHtml()` card that says what actually happened, rather than two empty rails that read like a search that found nothing. The query orders by `created_at` **then `id`**: the original seed rows share one timestamp, and without the tiebreak their order — and the category chips derived from it — would shuffle between loads. That derivation is why `categoryOrder()` is a function and not the constant it used to be: computed once at script load, it would freeze on an empty list. The detail screen is deliberately excluded from the live repaint because it may hold a half-typed review.
- **Every activity comes from the scraper, and its facts come from its own page.** `supabase/functions/scrape-activities/` uses Firecrawl on each listing page in `sources.json` only to *find* items (title, ages, link). Each item's own page is then parsed by `parseClubPage()` — deterministic code, no model — for weekdays, hours, price, season, description and signup link, and `refine()` rejects a row whose facts did not come from that parse (`_factsFromPage`), whose page is not about it (`pageIsAbout()`), or that lacks ages overlapping 12–18, days and hours (date and hour for a one-off), a price (0 only when the page says free), a signup link or a location. The model is kept away from facts because, checked against the pages, it invented schedules, prices and links (HANDOFF lists the cases). A page with several age groups (the museum) is read per slot, and only the slots whose grades overlap the row's count. Only sources with a parser for their item pages stay in `sources.json`. מרכז פריזמה is the one source without Firecrawl extraction: `coingRows()` reads coing.co's public API and takes days and hours from the organizer's description text by code (HANDOFF has the rules). On every source a price of 0 is stored only when the text says free in so many words (`FREE`), never because no price was found. Rows are upserted on `source_url` — the item's own page, with matnasnet's varying `ht` parameter stripped — so a re-run keeps ids, favourites and reviews; `source_page` marks a scraper row. `description` holds the page's prose, with schedule and price fragments stripped and text about young children rejected; `short_description` is left null so the detail screen doesn't print it twice. Weekly, one source per cron call, secret from Vault, ~50 credits a week — details in HANDOFF.
- **Social/follow system**: every account has an `is_private` flag (default `true`). Following a public account is instant (`follows.status = 'accepted'` right away); following a private one creates a `pending` row the target approves/denies from the Social tab. "Activities a followed user is into" deliberately shows their **favorites** (real, tracked data), never a fabricated "registered" status — the app has no real registration tracking (see Notes). Visibility is single-ruled: every signed-in account sees a profile's display name, username, counts, interests and achievements; its favourites, picture and banner are for whoever passes `canViewProfile()` (self, a public account, or an accepted follower of a private one) — the one gate both the UI and the `favorites_select_visible` RLS policy implement in parallel. **Known, deliberate gap**: profile-picture/detail privacy is enforced only at the UI layer (the app just doesn't fetch/render a photo it shouldn't) — the `avatars` storage bucket stays fully public-read regardless of `is_private` (pre-existing behavior, not introduced by this feature), and Postgres RLS can't hide one column while exposing others on the same `users` row. Real hardening would need a private bucket with signed URLs and/or a dedicated view.

### Backend: Supabase

- Schema is defined by `supabase/migrations/*.sql`, applied in filename (timestamp) order. Several tables were altered after their original creation — e.g. `activities` was dropped and completely rebuilt (48-field model) in a later migration, and `user_preferences` had its "vibe" quiz columns added then removed. Read the most recent migration touching a table for its current shape rather than the table's original `CREATE`.
- `public.users` is kept in sync with `auth.users` by an `on_auth_user_created` trigger (`handle_new_user()`) — every signup automatically gets a `public.users` row; there is no separate "create profile" step in the app code.
- RLS is enabled on every table. `activities` is publicly readable only where `is_published = true`; writes are gated by `public.users.role` (`organizer`/`admin`), not row ownership (the current activities model has no `created_by`). `registrations` and `user_preferences` are strictly owner-scoped (`auth.uid() = user_id`). `favorites` is insert/delete only (no update — a pure toggle), and its **select** policy (`favorites_select_visible`) is wider than owner-only: it also allows a public account's own rows, or an accepted follower's rows, to be read by the follower — see the social/follow system note above. `follows` (`follower_id`/`followee_id`/`status`) is readable by either participant; inserting an already-`accepted` row is only allowed when the target is actually public (checked server-side, not just client-side), so approval can't be bypassed by an insert.
- Avatars use Storage bucket `avatars` (public read); objects are stored at `<user_id>/<filename>`, with owner-only write enforced via RLS on `storage.objects`.
- `activity_reviews` is the one table here whose select policy is **owner-only on purpose**. Everyone else reads through `activity_reviews_public(p_activity_id)`, a `security definer` function that returns `display_name`/`avatar_url` as null for anonymous rows and never returns `user_id` at all. Exposing the table with `using (true)` would have shipped `user_id` on every row, and `users_select_all` is itself `using (true)` — so any client could have joined an "anonymous" review straight back to its author. Unlike the avatar-bucket gap below, this one is **not** a UI-level gate: anonymity is the default and the product promises it to minors, so it holds at the API. Anything that adds a second way to read reviews has to preserve that.
- **New tables need explicit `grant`s.** `auto_expose_new_tables` is unset in `supabase/config.toml`, so entities created in `public` are *not* reachable through the Data API roles without one. `favorites` and `follows` predate that default and got their grants implicitly, so copying their migrations verbatim produces a table that exists and rejects every write — `activity_reviews` grants `authenticated` explicitly (and deliberately not `anon`, which reads through the function instead).

## Notes

- The Supabase URL and publishable/anon key are hardcoded in `docs/index.html` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`) — this is intentional and safe, it's the public client key, not a secret.
- `registrations` exists in the schema but isn't wired into the UI — the "Register" CTA at the bottom of the activity detail overlay just opens its `registration_url` in a new tab; it never writes a `registrations` row.
- No offline support, by design — the PWA manifest only enables "Add to Home Screen," there is no service worker.
- `docs/variants/` is a **separate, self-contained set of 5 whole-app visual-direction explorations** (each a standalone HTML file sharing `docs/variants/activities.js` for demo data), built for a design review — not part of the production app and not linked from it. `docs/variants/index.html` is a side-by-side comparison gallery for them. Safe to ignore when working on the real app in `docs/index.html`.
